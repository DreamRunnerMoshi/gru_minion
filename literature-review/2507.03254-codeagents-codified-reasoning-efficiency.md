# CodeAgents: A Token-Efficient Framework for Codified Multi-Agent Reasoning in LLMs

- **Citation**: [arXiv:2507.03254](https://arxiv.org/html/2507.03254v1)
- **Cited in**: this file only, so far — candidate addition to [design/architecture/02-gru-minion-protocol.md](../design/architecture/02-gru-minion-protocol.md), see below

## Thesis

Expressing multi-agent reasoning/planning as executable code, rather than natural-language chain-of-thought prose, is substantially more token-efficient — and frequently *more* accurate, not a capability tradeoff for the token savings.

## Key findings

| Benchmark / model | Input tokens (code vs. NL) | Output tokens (code vs. NL) | Accuracy (code vs. NL) |
|---|---|---|---|
| VirtualHome | 5,845 vs. 10,462 (−44.2%) | 484 vs. 218 (+122%, code used *more* output tokens here) | 0.56 vs. 0.36 (+55% relative) |
| GAIA, Gemini-2.5-Flash | 23.28M vs. 72.42M | — | 62% vs. 56% (+10.7%) |
| GAIA, Gemini-2.5-Pro | 17.93M vs. 31.80M (−43.6%) | — | 65% vs. 62% (+4.8%) |
| HotpotQA, GPT-4.1 | 1.00M vs. 2.11M (−52.6%) | 42.21K vs. 110.74K (−61.9%) | 51% vs. 46% (+10.9%) |
| HotpotQA, LLaMA-4-Maverick | 1.58M vs. 5.71M (−72.3%), cost $0.32 vs. $1.08 | — | — |

Reported overall range: "reduces input and output token usage by 55–87% and 41–70% respectively" (Gemini-2.5-Flash on GAIA).

## What we took from it

**Directly reinforces the correction in [experiments/exp1/NOTES.md#tool-call-breakdown](../experiments/exp1/NOTES.md#tool-call-breakdown---what-completion-tokens-are-actually-spent-on)** with independent, controlled evidence: expressing reasoning as code (which is effectively what Qwen3.8-27B was doing in exp1 — embedding diagnostic Python scripts inside 31% of its tool calls, accounting for 73% of tool-call token volume) is not "cheap mechanical output competing with real reasoning" — it's plausibly the *more* token-efficient reasoning medium, not a lesser one. The VirtualHome row is a useful nuance: code reasoning can cost *more* output tokens per step (writing a precise script vs. a vague prose plan) while still winning heavily on total tokens, because it eliminates downstream re-explanation/re-reasoning that verbose prose otherwise requires.

**Design implication worth testing**: if minion is meant to do exploratory diagnosis (not just execute a fully-specified plan), deliberately encouraging code-based "reasoning" over prose CoT — e.g. via the system prompt, similar to how `swebench.yaml` already nudges toward "brief THOUGHT + a tool call" — may be a token-efficiency lever independent of model choice, consistent with what exp1 empirically observed by accident rather than by design.

## Caveats

Benchmarks are GAIA/HotpotQA/VirtualHome — general agentic reasoning and QA tasks, not SWE-bench-style coding tasks specifically, so the magnitude of the effect (40-87% reduction) shouldn't be assumed to transfer exactly. The VirtualHome output-token increase shows the effect isn't uniformly "code is cheaper on every axis" — worth keeping the nuance rather than over-generalizing to "code always saves tokens."
